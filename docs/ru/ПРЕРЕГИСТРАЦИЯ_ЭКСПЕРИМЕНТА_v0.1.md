## 1. Гипотеза и H0

**H1:** TR-Core + behavioral programs даёт статистически значимый transfer на genuinely unseen задачах (T1/T2/T3), и это улучшение обязано механизму развития (опыт → правила), а не самому наличию bp-слоя.

**H0:** transfer(TR-Core+bp) ≤ transfer(Base, без bp) на test-наборе при заданном уровне значимости.

Пороги принятия H1 — по Протоколу §4.4, §11 (с коррекцией Holm–Bonferroni).

## 2. Домен и словарь признаков

**Субъект** (взаимодействующая сущность):
| Атрибут | Значения |
|---------|----------|
| `role` | `{adult, child, elder}` |
| `friendliness` | `{warm, cold}` |
| `status` | `{insider, stranger}` |
| `mood` | `{calm, upset}` |

**Контекст взаимодействия** (часть наблюдения, считаем атрибутом):
| Атрибут | Значения |
|---------|----------|
| `context` | `{greeting, request, conflict}` |

**Действия** (action interface): `A = {approach, avoid, ask, obey}` (4 primitive action).

**Наблюдение** = набор attribute-value литералов, покрывающий все 5 атрибутов (полный контекст). Полное пространство контекстов: `3·2·2·2·3 = 72` различных.

---

## 3. Target program (oracle, «скрытая истина»)

Функция успеха `success(a | S₀, G) ∈ {0,1}` — **орaкул**, детерминированный, процедурно задан вне агента. G = уникальное правильное действие, вычисляемый так:

```
G(S₀):
  if role ∈ {adult, elder} and friendliness = warm  → approach
  else if role = child                              → approach
  else if context = conflict and status = stranger  → avoid
  else if mood = upset and context = conflict       → avoid
  else if mood = upset and context = request        → ask
  else if context = conflict and friendliness = cold→ obey
  else if role ∈ {adult, elder} and context = request → obey
  else (ничто из правил)                            → ask        (fallback)
```

Правило покрывает все 72 контекста однозначно (проверяется генератором: никаких конфликтов). Oracle **не известен агенту**; агент получает только outcome = 1/0 по своему выбору.

Шум: основной режим — детерминированный (noise=0). Флаг robustness-noise: outcome искажается с вероятностью ε=0.05.

## 4. Оси расхождения (genuinely unseen)

| Ось | Механизм | Правило генерации test | Проверка перекрытия (anti-memorization) |
|-----|----------|------------------------|------------------------------------------|
| **T1 — новое значение** | `role=elder` **отсутствует в train**; тест вводит его | test содержит контексты с `role=elder`, остальные атрибуты — как в train | train-генератор **запрещает** `role=elder` |
| **T2 — новая комбинация** | `(mood=upset, context=conflict)` **не встречается вместе в train**; обе части известны | test содержит контексты с этой парой (и с ролью из train) | train-генератор исключает пару `(mood=upset, context=conflict)` |
| **T3 — новое структурное взаимодействие** | новый **атрибут-размерность**, требующий **композиции** двух известных правил | test использует `role=elder` ВМЕСТЕ с `context=request, mood=calm` — для решения нужно применить правило по `role` + правило по `context` (COMPOSE) | train не содержит ни `role=elder`, ни пару `mood/context` из T3-описания |

T1/T2/T3 — раздельные test-наборы; каждый требует обобщения/композиции, не решаемых применением train-правила «в лоб» (проверяется trace-контролем, Протокол §6.1).

## 5. Генерация данных

**Train experience:** последовательность из M=600 контекстов (seed-генератор), равномерно по `72`-пространству **минус** запреты из §4 (без `role=elder`, без пары `upset+conflict`). Каждое взаимодействие: агент выбирает действие, получает outcome (правильно/нет). Агент **не** знает oracle и правильного действия напрямую.

**Known-контроль (retention):** фиксированный holdout из 120 контекстов той же train-распределённости.

**Test-наборы:** 
- T1: 60 контекстов с `role=elder` (с остальными атрибутами из train-пространства).
- T2: 60 контекстов с `(mood=upset, context=conflict)` + роли из train.
- T3: 40 контекстов, требующих композиции (из описания §4).
- Итого test: 160 контекстов.

Генерация всех наборов — **до прогона**, по seed-стратегии §8. Никаких test-данных в обучении.

## 6. Модели и конфигурации (абляции)

| Конфигурация (id) | bp-слой | train-опыт | Назначение |
|-------------------|---------|------------|------------|
| `base`            | ❌ | есть | H0: static-memory lookup (majority action по точному контексту из train-outcomes) |
| `full`            | ✅ (все 7 операций) | есть | гипотеза |
| `null_bp`         | ✅ | исходы = случайный шум | механизм vs опыт |
| `ab_no_generalize`| ✅ без GENERALIZE | есть | вклад обобщения |
| `ab_no_specialize`| ✅ без SPECIALIZE | есть | вклад специализации |
| `ab_no_compose`   | ✅ без COMPOSE | есть | вклад композиции (планируемо нулевой — см. §4 примечание) |
| `decision_list`   | ❌ (внешний) | есть | внешний baseline поверх train |

Внешний baseline: **decision-list learner (RIPPER-стиль)** с дефолтными гиперпараметрами (фиксируется в prereg). Обучается на том же train (по outcome-свёрнутым примерам «контекст → правильное действие», реконструируемым из логирования outcome), тестируется на том же test (T1/T2/T3), те же integrity-ограничения.

> **Примечание по COMPOSE.** В v0.1-задачах COMPOSE (суперпозиция поведения — по v0.2 это `run(subprogram)`) не имеет нетривиальной выразительной ниши: все переносимые необходимые конъюнкции выразимы через путь GENERALIZE→SPECIALIZE. Поэтому `ab_no_compose == full` планируемо (null-контроль). Демонстрация композиции как отдельной операции — задача для v0.2, фиксируемая как ограничение области применимости, а не как пробел механизма.

|----------|----------|
| `N_min` | 3 |
| `P_min` | 0.7 |

| `sep_min` | 0.2 |
| `validate_accuracy` | 0.8 |
| `validate_margin` | 0.05 |
| `develop_interval` | 50 (шагов опыта) |
| `max_condition_literals` | 2 |
| `min_coverage` | 3 (explore-триалов на кандидата) |

Индукция (`develop`) валидирует кандидатов **только по unbiased explore-триалам** (uniform-random действия в рамках `explore_rate`): это устраняет selection bias от собственной политики агента. Гипотеза, прошедшая порог `validate_accuracy + validate_margin` при покрытии ≥ `min_coverage`, материализуется; обобщения, переставшие держать порог, демоутятся (RETIRE) на следующем проходе.

## 8. Seed-стратегия

Для каждого запуска `i ∈ {1..N}` три независимых генератора:

- `rng_agent = Random(SEED_BASE + i)` — внутренние решения агента.
- `rng_env   = Random(SEED_BASE + 10_000 + i)` — генерация train/test/oracle.
- `rng_noise = Random(SEED_BASE + 20_000 + i)` — шум (если включён).

`SEED_BASE = 1000`. N определяется power analysis (таргет ≥0.80, d≥0.5); **pre-registered N=24** (зафиксирован по power-пилоту, см. §12). Для 3 primary-сравнений (full>base, full>ab_no_generalize, full>null_bp) достигается dz≥5 при N=24 (запас мощности >0.99).

**Replication:** второй независимый блок из N' запусков с `SEED_BASE=9000`, те же правила.

## 9. Протокол прогона (по §9 Протокола)

1. Генерация всех наборов (train/known/T1/T2/T3) на seed-стратегии.
2. Для кажdoго `i`: агент проходит M=600 контекстов, программа развивается → freeze → evaluate на test (T1,T2,T3) и known.
3. Developmental-кривая: точки опыта 10% / 25% / 50% / 100% (после каждой — freeze+evaluate test).
4. Chance/ceiling: chance = случайный выбор действия на test; ceiling = перфектный use oracle на test (по определению 1.0, но мерим для отчёта).
5. Сбор метрик: transfer по T1/T2/T3, суммарный, anti-memorization trace-доля, retention(known), сложность C, число правил/revisions.
6. Стат-анализ: per-seed единица → парный **permutation test** (distribution-free, 20k ресемплов; заменяет t-тест ввиду отсутствия scipy в окружении), Cohen's d_z, bootstrap-CI (2000 ресемплов), Holm–Bonferroni по семейству сравнений.
7. Ablation vs Full; Null-bp vs Full; внешний baseline vs Full.
8. Replication-блок; отчёт.

## 10. Метрики и пороги (сводка)

| Метрика | Определение | Порог для H1 |
|---------|-------------|--------------|
| **Transfer (primary)** | accuracy на T1+T2+T3 (усреднено по seed) | full > base, парный permutation p<0.05 (Holm–скорр. по семейству {full>base, full>ab_no_generalize, full>null_bp}), d_z≥0.5; ≥2 из 3 осей значимо |
| Anti-memorization | доля успешных unseen, требующих GENERALIZE/SPECIALIZE | ≥ 0.7 усреднённо (иначе H1 не принимается) |
| Retention (known) | accuracy на known | known(full) ≥ 0.7 и known(full) ≥ known(ab_no_generalize)+0.1 |
| Developmental тренд | регрессия transfer ~ log(объём опыта) | p<0.05, положительный коэффициент |
| C (сложность) | формула v0.2 §6 | мониторинг, флаг при C>200 |
| Robustness (ε=0.05) | transfer при шуме | не рушится мгновенно (< -0.15 vs без шума) |

## 11. Критика протокола (самопроверка перед фиксацией)

- [ ] True unseen: `role=elder` и пара `upset+conflict` не присутствуют в train (генератор проверяет)
- [ ] Нет leakage: oracle/test недоступны агенту и механизму развития
- [ ] Freeze на тесте: программа не дообучается на test
- [ ] Per-seed единица анализа
- [ ] Гиперпараметры внешнего baseline дефолтные, не тонированные
- [ ] Х2 chance/ceiling присутствуют
- [ ] Developmental-кривая и traces запланированы
- [ ] Пре-registered до прогона; изменения — только как post-hoc

## 12. Открытые вопросы для утверждения (перед fix)

1. **Выразительность COMPOSE.** Закрыто (см. §6): в v0.1 COMPOSE — `ab_no_compose == full` (null-контроль). Демонстрация — задача v0.2.
3. **Объёмы выборок.** Закрыто power-пилотом: `N=24`, M=600, known=120, T1=60/T2=60/T3=40. При N=24: все 3 оси `full>base` значимы (dz=3.1–5.4), retention-пороги met (known(full)=0.79≥0.7 и ≥known(ab_no_gen)+0.1). Возможно сокращение N до 6–8 при сохранении мощности >0.9 на primary-сравнениях (dz≥5.6); N=24 — консервативный запас на вторичные сравнения.

**Закрытые решения.**
- Внешний baseline: **decision-list learner (RIPPER-стиль)**, гиперпараметры — дефолтные, фиксируются в этом документе (§6).
- Масштаб пространства: **72 контекста**.
- Статистика: парный **permutation test** (+Cohen's d_z, bootstrap-CI, Holm–Bonferroni); distribution-free, без предположения о нормальности.
- COMPOSE в v0.1: планируемо **null-контроль** (см. §6 примечание); его демонстрация выносится в v0.2.
- Объёмы: **N=24**, seed-стратегия §8.

Оставшиеся пункты (объёмы выборок) решаются в **пилоте**, до фиксации. После пилота — зафиксированный пре-registration, и только потом основной прогон.
