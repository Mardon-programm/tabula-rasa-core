# TR-Core Behavioral Program Specification v0.1

> Формализация исследовательской модели: превращение опыта в исполняемую программу поведения.
> Без кода, без реализации — только сущности, жизненный цикл правила, механизмы развития и критерии «реального развития».

---

## 1. Исследовательская постановка

### 1.1 Суть

> **«Исследую механизм развития искусственного интеллекта: как минимальная когнитивная архитектура может приобретать и модифицировать исполняемые программы поведения непосредственно из опыта».**

### 1.2 Центральная гипотеза

> Можно ли получить всё более сложное и адаптивное поведение из **маленького фиксированного когнитивного substrate**, если приобретённый опыт преобразуется в **исполняемые программы поведения**, а эти программы способны **пересматриваться, обобщаться и комбинироваться**?

### 1.3 Доказательный критерий (primary criterion)

> **Одна и та же фиксированная архитектура должна становиться способнее благодаря собственному опыту, причём улучшение должно проявляться на ситуациях, которых она раньше не видела** (generalization / transfer to unseen situations).

Это отличает «развитие» от простого запоминания: если улучшение видно только на данных обучения — это переобучение, а не развитие.

---

## 2. Два уровня архитектуры

### 2.1 Фиксированный substrate (минимальное врождённое ядро)

Стабилен, изменению поведенческой программой **не подлежит**:

```
perception            — восприятие
memory                — память
learning / induction  — обучение / индукция
evaluation            — оценка результата
action interface      — интерфейс действий
interpreter           — интерпретатор правил/программ
revision mechanism    — механизм модификации приобретённых программ
```

### 2.2 Развивающийся behavioral program (изменяемый слой)

Всё поведение, которое нарабатывается из опыта:

```
rules / conditions / actions
concepts
strategies
preferences
valuations
social models
abstractions
```

**Принцип** (обязателен для v0.1):
Behavioral program — **отдельный изменяемый слой**, который substrate исполняет, но который не может произвольно менять сам substrate.

Это необходимо, чтобы экспериментально доказать, что развитие происходит **за счёт приобретённой программы**, а не потому, что в ядро постоянно добавляются новые механизмы.

```
┌───────────────────────────────┐
│       FIXED SUBSTRATE         │
│ perception / memory / learner │
│ evaluator / interpreter       │
└───────────────┬───────────────┘
                │
                ▼
┌───────────────────────────────┐
│     BEHAVIORAL PROGRAM        │
│ rules / concepts / strategies │
│ valuations / abstractions     │
└───────────────┬───────────────┘
                │
                ▼
              ACTION
```

## 2a. Три жёстких научных ограничения (integrity эксперимента)

Эти ограничения **обязательны** на всём эксперименте. Нарушение любого из них аннулирует доказательность: результат перестаёт быть «развитием», превращаясь в leak/memorization/tunаble-architecture.

**Ограничение 1 — Transfer должен быть genuinely unseen.**
Новая ситуация считаеттся «unseen» только если её невозможно решить одним лишь переносом уже знакомого набора признаков. Если новый контекст — это просто изменение значения уже изученной переменной (`greeting → conflict`), это **не** transfer, это вариация known. Genuine unseen означает появление **новых признаков/структуры, отсутствовавших в train**, таких, что ни одно выученное правило не срабатывает напрямую без обобщения/композиции.

**Ограничение 2 — GENERALIZE (и любые операции развития) не могут использовать тестовые данные.**
Проверка гипотезы абстракции может опираться только на **train experience**. Использование unseen/test-данных при формировании или валидации правил = **leakage**. Это искажает transfer и делает эксперимент невалидным.

**Ограничение 3 — Fixed substrate буквально frozen на всём эксперименте.**
Включая сам **revision mechanism** (механизм модификации программ). Никакой механизм нельзя добавлять/менять между экспериментами «чтобы архитектура стала способнее». Всё, что меняется — это **только behavioral program**. Иначе улучшение объясняется изменением архитектуры, а не развитием программы.

## 3. Минимальный behavioral-program formalism

Поток исполнения:

```
Observation
    ↓
State / Context
    ↓
Rule
    ↓
Condition
    ↓
Action / Subprogram
    ↓
Outcome
    ↓
Evaluation
    ↓
Revision
```

### 3.1 Сущности

| Сущность | Определение |
|----------|-------------|
| **Observation** | Сенсорный вход, получаемый substrate-ом. |
| **State / Context** | Распознанная ситуация: выделенные признаки и их значения. |
| **Rule** | Единица поведения: `IF condition THEN action/subprogram`. |
| **Condition** | Предикат над признаками текущего контекста. |
| **Action / Subprogram** | Исполняемое действие или вызов композитной программы. |
| **Outcome** | Фактический результат выполнения действия. |
| **Evaluation** | Сравнение ожидаемого и фактического результата. |
| **Evidence** | Накопленная статистика по правилу (успехи/ошибки в контекстах). |

### 3.2 Операции языка развития TR-Core

Единственный разрешённый набор операций над behavioural program (ровно семь):

```
CREATE        — создать правило/программу из нового опыта
MODIFY        — изменить условие/действие существующего правила
GENERALIZE    — заменить несколько частных правил общей абстракцией
SPECIALIZE    — добавить недостающий контекстный признак
COMPOSE       — соединить правила в композитную программу
SPLIT         — разделить правило по контексту на несколько
DELETE        — удалить правило (последнее средство)
```

Это и есть **язык развития TR-Core**: поведение меняется только перечисленными операциями через substrate-механизм модификации, никогда напрямую.

> **Примечание про `RECONTEXTUALIZE`:** он **не** является отдельной primitive operation. «Переобучение по контексту» реализуется составной последовательностью: **discover missing contextual variable → SPECIALIZE / SPLIT**. Язык остаётся минимальным (семь операций), DSL не разрастается.

## 4. Жизненный цикл правила

```
                    CREATE
                       │
                       ▼
                     TEST
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
          SUCCESS             FAILURE
             │                   │
             ▼                   ▼
       STRENGTHEN         ACCUMULATE EVIDENCE
                               │
                               ▼
                         CONTEXT ANALYSIS
                               │
             ┌─────────────────┼─────────────────┐
             ▼                 ▼                 ▼
          NOISE           SPECIALIZE         GENERALIZE
             │                 │                 │
             └─────────────────┴─────────────────┘
                               │
                               ▼
                         RE-EVALUATE
                               │
                               ▼
                         PERSIST / REPLACE
                               │
                               ▼
                            DELETE
                         (last resort)
```

### 4.1 Ключевые принципы пересмотра

**1. Одна ошибка ≠ неправильное правило.**
Правило НЕ меняется при единичном отклонении. Система накапливает evidence:

```
rule R: expected → outcome X
observed: X X X Y X
```

Пока статистики недостаточно — правило сохраняется. Иначе агент разрушает собственное знание из-за случайного события.

**2. Ошибка → поиск недостающего контекстного признака → SPECIALIZE.**
Не удалять знание, а уточнить условие:

```
IF person = familiar            IF familiar AND context = greeting → positive
THEN positive_response     →    IF familiar AND context = conflict → negative
```

**3. Обнаружение устойчивого класса → GENERALIZE / RESTRUCTURE.**
Обобщение — это **гипотеза абстракции**, которую надо проверять:

```
A → positive
B → positive   →  A,B,C share P  →  IF P THEN behavior X
C → positive
```

```
specific rules
     ↓
hypothesis of abstraction
     ↓
test on known + novel cases
     ↓
validated abstraction
     ↓
replace/compress subordinate rules
```

Обобщение не просто удаляет старые правила — оно заменяет/сжимает их **только после валидации**.

**4. DELETE — только последний уровень.**
Удалять, если накопленные наблюдения показывают систематическую ошибку, и SPECIALIZE / GENERALIZE / SPLIT (в т.ч. их составная последовательность для переобучения по контексту) не объясняют её:

```
DELETE(R)
    ↓
generate replacement hypothesis
    ↓
learn new rule/program
```

**Принцип:** *TR-Core не переписывает себя из-за ошибки; он объясняет ошибку.*

---

## 5. Ошибка как источник опыта

Ошибка не просто «чинится» — она **сама становится опытом**:

```
rule predicted X
actual outcome = Y
       ↓
experience: "context C invalidates rule R"
       ↓
learning
       ↓
new behavioral program
```

Система учится не только «что работает», но и **«где моё собственное знание перестаёт работать»**. Это основа настоящего developmental loop (знание о границах собственного знания).

---

## 6. Итоговый developmental loop

```
фиксированное ядро
    → опыт
    → программа поведения
    → действие
    → ошибка/успех
    → анализ контекста
    → специализация / обобщение / композиция
    → новая программа
    → проверка на невиданных ситуациях
    → (повтор)
```

## 7. Эксперимент (протокол, не код)

### 7.1 Дизайн

Даём агенту **последовательность опыта, которую он заранее не знает**. После обучения проверяем на **новых ситуациях, которых не было в обучающем опыте**.

**Сравнение:**

```
Baseline: memory + prediction + planner
   vs.
TR-Core + behavioral programs
```

### 7.2 Метрики

**Primary (доказательный):**
- **generalization / transfer to unseen situations** — поведение на невиданных ситуациях после опыта.

**Secondary:**
- adaptation speed — скорость адаптации при смене контекста
- recovery — восстановление после исключений/сбоев
- rule/program complexity — сложность накопленной программы
- sample efficiency — эффективность использования опыта
- retention — сохранение старого знания
- number of revisions — число пересмотров правил
- robustness against noise — устойчивость к шуму

### 7.3 Что НЕ является доказательством

- «агент стал вести себя умнее» на обучающих данных;
- красиво работающий rule engine без измеримого переноса на новое;
- добавление новых механизмов в ядро в ходе «обучения».

Если показано **экспериментально измеримое развитие + перенос на новые ситуации** — только тогда TR-Core из проекта превращается в R&D.

---

## 8. Границы v0.1 (что намеренно вне объёма)

- Нет реализации / кода.
- Нет решения, как именно кодировать `condition` / `action` (синтаксис правил).
- Нет критерия «достаточность evidence» (порог статистики) — выносится в v0.2.
- Нет механизма, как именно ищется «недостающий контекстный признак» при SPECIALIZE — выносится в v0.2.
- Нет конкретной метрики сложности программы — выносится в v0.2.

Эти пункты остаются **открытыми решениями**, которые надо зафиксировать до реализации.

---

## 9. Согласованные решения (fixed for v0.1)

1. **Пересмотр правил — иерархический:** NOISE → SPECIALIZE → GENERALIZE → DELETE (последнее средство).
2. **Одна ошибка ≠ сломать правило** — сначала накопление evidence.
3. **Ошибка сама становится опытом** (знание о границах знания).
4. **Behavioral program — отдельный изменяемый слой;** substrate фиксирован.
5. **Primary criterion = transfer** (обобщение/перенос на невиданные ситуации); secondary метрики перечислены в §7.2.
6. **Обобщение — гипотеза, которую надо валидировать**, а не слепое сжатие.
7. **Три жёстких ограничения integrity (см. §2a):**
   - Transfer = genuinely unseen (не просто вариация известных признаков);
   - операции развития **не** используют тестовые данные (нет leakage);
   - fixed substrate **frozen** на всём эксперименте, включая revision mechanism.
8. **`RECONTEXTUALIZE` не является отдельной операцией** — реализуется как `discover missing contextual variable → SPECIALIZE / SPLIT`. Язык = ровно семь операций (§3.2).
