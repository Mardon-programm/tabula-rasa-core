# TR-Core Behavioral Program Specification v0.2

> Продолжение `СПЕЦИФИКАЦИЯ_BEHAVIORAL_PROGRAM_v0.1.md` (далее — «v0.1»).
> v0.2 **закрывает открытые решения v0.1 §8**: синтаксис `condition`/`action`, порог evidence, механизм поиска недостающего контекстного признака при SPECIALIZE, мера сложности программы.
>
> Единый формализм для последующей реализации и прогона по `ПРОТОКОЛ_ИССЛЕДОВАНИЯ_v0.1.md`.

---

## 1. Исходные принципы (наследуются из v0.1)

1. Поведение меняется **только** семью операциями: `CREATE, MODIFY, GENERALIZE, SPECIALIZE, COMPOSE, SPLIT, DELETE`.
2. Behavioral program — **отдельный изменяемый слой**; substrate фиксирован.
3. Одна ошибка ≠ сломать правило → сначала накопление evidence.
4. Ошибка сама становится опытом.
5. Обобщение — гипотеза, которую валидируют, а не слепое сжатие.
6. Операции развития **не используют** test-данные (нет leakage).
7. Всё ниже — кандидаты на параметры, которые в обязательном порядке фиксируются в pre-registration (ПРОТОКОЛ §8).

## 2. Синтаксис behavioral program

### 2.1 Сущности

**Program** = конечный кортеж правил + регистр связей (композиций).

**Rule** — пара `(condition → action)` с метаданными:

```
Rule:
  id            : правило обладает уникальным id
  condition     : {}
  action        : action-выражение
  evidence      : статистика (см. §3)
  status        : LATENT | ACTIVE | RETIRED | DELETED
  provenance    : история операций (какие операции и когда применялись)
  created_step  : шаг (или условный момент) создания
```

`status`:
- `LATENT` — создано, но ещё не подтверждено достаточным evidence (не влияет на выбор действия).
- `ACTIVE` — подтверждено, участвует в исполнении.
- `RETIRED` — перестало выбираться (обобщено/замещено), история сохраняется.
- `DELETED` — удалено (последнее средство), история сохраняется для аудита.

### 2.2 Condition

**Condition** — конъюнкция литералов. **Литерал** — троичное выражение:

```
attribute  operator  value
```

- `attribute` — именованный признак (из perception substrate).
- `operator` ∈ `{=, ≠, ∈}` (`∈` — для категориальных множеств).
- `value` — константа или переменная (см. §2.4 по GENERALIZE).

Правило матчинга:
- Предикат выполнен, когда **все** литералы конъюнкции истинны на текущем контексте.
- Пустая конъюнкция («всегда») допустима — соответствует безусловному действию.

### 2.3 Action (действие / подпрограмма)

**Action** — один из двух типов:

1. **Primitive action** — непосредственно вызываемое действие из action interface substrate:
   ```
   do(<primitive>)          # напр. do(nothing), do(advance), do(greet_user)
   ```
2. **Subprogram call** (для COMPOSE):
   ```
   run(<program_id>)        # выполнение композитной подпрограммы
   ```
   Композиция не является вложенным интерпретатором произвольного кода — это **фиксированный реестр подпрограмм**, которые вызываются как единое действие.

### 2.4 Переменные и GENERALIZE

GENERALIZE вводит **переменные** в литералы:

```
IF person ∈ Colors  THEN positive     # person — переменная
```

Правила соответствия для обобщения:
- Обобщение заменяет константу на переменную **только если** валидация (§6 v0.1) на train подтверждает гипотезу (все экземпляры переменной ведут себя одинаково в контексте правила).
- Одно обобщение = одна замена константы на переменную за шаг (минимальный шаг, контролируемость).
- Каждая переменная типизирована (множество допустимых значений), чтобы не допускать бессмысленных обобщений.

### 2.5 Исполнение (интерпретатор) при выборе действия

**Порядок разрешения (deterministic, specificity-first):**

1. Из `ACTIVE` правил собрать все, чьи condition выполнены.
2. Отсортировать по **специфичности убывающей**: больше констант > больше литералов; при равенстве — больше суммарный evidence (примерка «доверяй проверенному»).
3. **Первое** сработавшее правило определяет действие.
4. Если сработавших нет:
   - есть `LATENT` с подходящим condition → действие LATENT-правила с минимальным риском (exploration с ограничением, см. §3.3), либо fallback substrate (curiosity/планирование);
   - иначе — fallback substrate (планирование/исследование) и запись наблюдения.

Этот порядок фиксирован в substrate и не меняется в ходе эксперимента (интегrity, v0.1 §2a).

## 3. Evidence и критерий «достаточность»

### 3.1 Статистика правила

Для каждого `ACTIVE`/`LATENT` правила substrate ведёт:

```
evidence:
  n_success    : число подтверждений (ожидаемый outcome достигнут)
  n_failure    : число подтверждённых нарушений
  success_rate : n_success / (n_success + n_failure)
  last_updated : момент последнего обновления
```

Учёт ведётся **по правилу**, а не по отдельному контексту, но при SPECIALIZE/SPLIT счётчики **наследуются** в производные правила (с пометкой provenance), чтобы не терять историю.

### 3.2 Порог «достаточность evidence»

Правило переходит `LATENT → ACTIVE`, когда **все** условия:

```
n_success >= N_min           (N_min = 3, параметр pre-registration)
success_rate >= P_min        (P_min = 0.7, параметр)
```

Значения по умолчанию фиксируются в pre-registration **до** прогона.

Правило **не** переходит в ACTIVE, если evidence противоречит (failures опознаны как систематические, §4).

### 3.3 Активный выбор LATENT-правила (ограниченная проба)

Чтобы собрать evidence, LATENT-правило может исполняться с вероятностью `explore_rate` (по умолчанию 0.2, параметр). Это **ограниченная проба**: частота ниже, чем у ACTIVE; направляется туда, где fallback-планировщик уже не уверен. Это не подгонка под тест: проба происходит **только на train-опыте**, никогда на test (ПРОТОКОЛ §7.2).

## 4. Иерархический пересмотр при ошибке

Вход: правило `R`, правило сработало, `outcome ≠ expected`.

### 4.1 Этап 0 — Накопление (не трогать)

Одна ошибка ≠ сломать правило (v0.1 §4.1). Ошибка регистрируется в evidence; если нарушений меньше порога — только фиксация.

Порог перехода к анализу:

```
n_failure >= F_min          (F_min = 3, параметр)
n_failure / (n_success + n_failure) >= D_min   (D_min = 0.3, параметр)
```

До достижения порога никакие операции над правилом не выполняются.

### 4.2 Этап 1 — Контекстный анализ (найти недостающий признак)

Цель — найти признак, который **дискриминирует** успешные и неуспешные случаи срабатывания `R`.

Алгоритм substrate `find_discriminating_feature(R)`:

1. Собрать историю срабатываний `R`: множество положительных и отрицательных примеров (контексты успеха/фейла).
2. Для каждого атрибута `attr`, отсутствующего в condition правила, вычислить **separation score**:
   ```
   sep(attr) = |P_attr - N_attr|  /  1   (нормированная разность долей
                                          значения в успехе vs фейле)
   ```
   где P_attr — доля успешных примеров, содержащих `attr=value`; N_attr — доля неуспешных.
3. Выбрать атрибут с **максимальным разделением**, при sep выше порога `sep_min` (параметр, default 0.2).
4. Вернуть `(attr, value_split)`.

Если дифференцирующего признака нет (все sep < sep_min) — перейти на этап 2 (проверка GENERALIZE/SPLIT), затем этап 3 (DELETE).

### 4.3 Этап 2 — Применить операцию по результату анализа

- **Найден дифференцирующий признак** → **SPECIALIZE** (v0.1 §4.2): добавляем найденный литерал в condition. Если расхождение делит данные на несколько устойчивых групп → **SPLIT** на несколько правил (каждое с добавленным признаком). Производные правила наследуют evidence (с provenance).
- **Признака нет, но фейлы стабильны и не объясняются контекстом** → **GENERALIZE или RESTRUCTURE**, если есть гипотеза абстракции, подтверждаемая только train (см. v0.1 §4.3 и §2.4 настоящей спецификации).
- **Ни одно из вышеперечисленного не объясняет систематическую ошибку** → этап 3.

### 4.4 Этап 3 — DELETE (последнее средство)

```
DELETE(R)
   ↓
generate replacement hypothesis (новое CREATE)
   ↓
learn new rule (обучение заново, с пустым evidence)
```

DELETE — только после того, как SPECIALIZE / SPLIT / GENERALIZE не объяснили ошибку (v0.1 §4.4).

**Принцип сохраняется:** TR-Core не переписывает себя из-за ошибки; он объясняет ошибку.

## 5. Обобщение (GENERALIZE) — формализация валидации

Обобщение — гипотеза, которую нужно проверить **на train** (без test, v0.1 §2a).

### 5.1 Процедура

1. Выделить группу правил с идентичной структурой action и «соседними» condition (различаются только константой на одной позиции).
2. Сформировать гипотезу замены константы на **типизированную переменную** (одна позиция, один шаг).
3. **Валидация на train:** пройти по train-опыту; гипотеза подтверждена, если у всех известных экземпляров переменной наблюдаемый успех совпадает с предсказанным обобщённым правилом (в пределах порога `validate_accuracy`, параметр, default 0.8).
4. При подтверждении: `RETIRE` исходные, `CREATE` обобщённое правило, перенести evidence (provenance).
5. Без подтверждения: гипотеза отклоняется, правило не меняется.

### 5.2 Запрет

Обобщение **не** использует test-данные (ПРОТОКОЛ §3, v0.1 §2a Оп 2). Любая проверка — только по train-опыту, уже пережитому агентом.

## 6. Мера сложности программы (complexity)

Используется: (а) в complexity-регуляризации (ПРОТОКОЛ §6.5); (б) как secondary-метрика.

### 6.1 Определение

```
C(program) = Σ_rules ( base + w_lit · n_literals + w_var · n_variables )
             + w_prog · n_subprograms
             + w_depth · max_compose_depth
```

| Параметр | Значение по умолчанию | Назначение |
|----------|------------------------|------------|
| `base` | 1 | базовая стоимость каждого правила |
| `w_lit` | 1 | стоимость одного литерала condition |
| `w_var` | 2 | стоимость одной переменной (обобщение дороже факта) |
| `w_prog` | 3 | стоимость композитной подпрограммы |
| `w_depth` | 2 | штраф за глубину композиции |

Все веса — параметры, фиксируются в pre-registration.

### 6.2 Использование

- **Secondary-метрика:** `C` отслеживается на протяжении развития (ПРОТОКОЛ §6.6 developmental-кривая включает траекторию сложности).
- **Complexity-регуляризация:** эффективный перенос считается с оговоркой, если он достигнут только при росте `C` выше заданного порога `C_max` (параметр). Порог фиксируется до прогона; превышение фиксируется как ограничение интерпретируемости (ПРОТОКОЛ §6.5).

## 7. Операции и их интерфейс (полный справочник)

| Операция | Сигнатура | Условия применимости | Результат |
|----------|-----------|----------------------|-----------|
| **CREATE** | `CREATE(cond, action) -> rule` | cond/action синтаксически валидны | Новое `LATENT`-правило, evidence=0, provenance=[CREATE] |
| **MODIFY** | `MODIFY(id, cond', action')` | правило ACTIVE/LATENT; изменение обосновано ошибкой или валидацией | condition/action заменены; evidence сохраняется с пометкой |
| **SPECIALIZE** | `SPECIALIZE(id, attr, val)` | нашёлся дискриминирующий признак (§4.2) | В condition добавлен литерал; evidence наследуется |
| **SPLIT** | `SPLIT(id, attr, {group1..groupk})` | признак делит историю на k устойчивых групп | k правил, каждое с литералом; evidence делится по группам |
| **GENERALIZE** | `GENERALIZE(group_ids, var_pos)` | гипотеза валидирована на train (§5.1) | Исходные RETIRED, создано обобщённое правило |
| **COMPOSE** | `COMPOSE(program_a, program_b) -> program_id` | обе подпрограммы ACTIVE и согласованы по выходам/входам | Зарегистрирована подпрограмма `run(program_id)` |
| **DELETE** | `DELETE(id)` | только после этапа 0–2 не объяснили ошибку (§4.4) | `DELETED`, история сохраняется |

Все операции исполняются **только** substrate-механизмом модификации (фиксированный), и не доступны как произвольный код из behavioral program (v0.1 §2).

## 8. Параметры, фиксируемые в pre-registration (сводка)

| Параметр | Умолчание | Где определён |
|----------|-----------|----------------|
| `N_min` | 3 | §3.2 (порог evidence) |
| `P_min` | 0.7 | §3.2 (мин. success_rate для ACTIVE) |
| `explore_rate` | 0.2 | §3.3 (вероятность пробы LATENT) |
| `F_min` | 3 | §4.1 (мин. фейлов для анализа) |
| `D_min` | 0.3 | §4.1 (доля фейлов для анализа) |
| `sep_min` | 0.2 | §4.2 (мин. разделение признака) |
| `validate_accuracy` | 0.8 | §5.1 (порог валидации GENERALIZE) |
| `base, w_lit, w_var, w_prog, w_depth` | 1,1,2,3,2 | §6.1 (мера сложности) |
| `C_max` | — (задаётся до прогона) | §6.2 (порог регуляризации) |

Хотя значения умолчаний обоснованы, в pre-registration они фиксируются **явно**, до прогона, и не меняются задним числом.

## 11. Согласованные решения (fixed for v0.2)

1. **Синтаксис правил:** конъюнкция литералов `attribute operator value`, операторы `{=, ≠, ∈}`, переменные для GENERALIZE, action = primitive или subprogram call.
2. **ACTIVE/LATENT/RETIRED/DELETED** статус-модель правила; LATENT-правила исполняются ограниченно (explore_rate).
3. **Evidence:** правило подтверждается при `n_success ≥ N_min` и `success_rate ≥ P_min`; анализ ошибки запускается при `n_failure ≥ F_min` и доле фейлов `≥ D_min`.
4. **SPECIALIZE/SPLIT:** поиск дифференцирующего признака через separation score, с порогом `sep_min`.
5. **GENERALIZE:** замена константы на типизированную переменную только после валидации на train (`validate_accuracy`).
6. **DELETE:** последнее средство, после исчерпания SPECIALIZE/SPLIT/GENERALIZE.
7. **Мера сложности:** аддитивная формула §6.1 с фиксируемыми весами.
8. Все параметры из §8 — pre-registered до прогона.
